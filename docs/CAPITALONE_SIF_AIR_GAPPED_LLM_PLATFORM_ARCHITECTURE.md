# CapitalOne Air-Gapped Internal AI/LLM Serving Platform - Finalized Architecture

**Codename:** Sentinel Air-Gapped Inference Fabric (SIF-A)
**Author / Owner:** Principal Engineer, AI Inference Platform
**Audience:** Senior Leadership, Platform Engineering, Security Architecture, SRE, LOB Architecture Councils
**Status:** Finalized internal architecture - production-grade
**Platform analogue:** A self-contained, private AWS EKS based LLM serving platform for regulated workloads that require no public internet dependency, controlled artifact import, enclave-local identity, strict RBAC, and complete auditability.

---

## Section 1 - Executive Summary

CapitalOne needs an internal LLM serving environment for workloads whose data handling, regulatory posture, or operational risk profile requires an air-gapped deployment model. This includes PCI-scoped workflows, fraud and risk intelligence, sensitive customer servicing, restricted model evaluation, and workloads where prompts, completions, model weights, logs, and intermediate KV cache state must never depend on public SaaS control planes or public internet paths.

**Sentinel Air-Gapped Inference Fabric (SIF-A)** is the production architecture for that environment. It extends the Sentinel Inference Fabric operating model into a disconnected enclave: private EKS clusters, private registries, private model storage, enclave-local identity, private certificate authorities, signed artifact import, deterministic deployment pipelines, and observability that runs entirely inside the boundary.

The platform is not simply "SIF without internet." It is a complete trust and operations model:

- **No public runtime dependency:** inference, routing, model staging, telemetry, billing, and authentication continue to operate when the enclave has no internet route and no public DNS dependency.
- **Controlled artifact ingress:** container images, Helm charts, OS packages, GPU drivers, model weights, LoRA adapters, policy bundles, vulnerability databases, and documentation are imported through a signed, scanned, approved, and audited transfer process.
- **Enclave-local authentication and authorization:** human users authenticate through an internal identity provider inside the enclave; workload identity is issued through SPIFFE/SPIRE; Kubernetes and application RBAC are generated from tenant and platform roles.
- **Strong tenant isolation:** namespaces, network policy, IAM boundaries, SPIFFE identities, KMS encryption, cache namespaces, and quota boundaries are generated by the control plane.
- **Production LLM operations:** KServe, vLLM, vLLM Router, LMCache, NVIDIA GPU Operator, DCGM Exporter, Prometheus, Grafana, OpenTelemetry, Vault, Gatekeeper/Kyverno, Falco, and signed GitOps are operated as first-class platform components.

SIF-A gives LOBs the same self-service serving experience as the connected SIF platform: register a tenant, request Tier 1, Tier 2, or Tier 3 capacity, select approved models and LoRA adapters, attach cost center and compliance tags, and receive an internal endpoint. The difference is that every control-plane dependency, every artifact source, and every security service is local to the enclave and auditable.

## Section 2 - Air-Gapped Operating Model

SIF-A is organized around one core rule:

```
No production runtime component may depend on a public network, public package
repository, public identity provider, public telemetry endpoint, or mutable
artifact source outside the enclave.
```

The enclave has three zones:

```
                            CONNECTED ENTERPRISE ZONE
                  corporate source, enterprise IdP, external repos
                                      |
                                      | signed export packages only
                                      v
+----------------------------------------------------------------------------+
|                         CONTROLLED TRANSFER ZONE                            |
|  malware scan | SAST/SCA | SBOM validation | signature verify | approvals   |
|  model scan   | license policy | provenance check | immutable import log    |
+----------------------------------------------------------------------------+
                                      |
                                      | one-way approved import bundle
                                      v
+----------------------------------------------------------------------------+
|                            AIR-GAPPED ENCLAVE                               |
|                                                                            |
|  Private EKS | private ECR/Harbor | private Git | private Helm/OCI repo    |
|  S3/FSx model registry | Vault | Keycloak | SPIRE | KMS/HSM | OTel stack    |
|  KServe | vLLM | LMCache | GPU Operator | DCGM | Sentinel Router          |
|                                                                            |
+----------------------------------------------------------------------------+
```

**Connected enterprise zone** is where source code is authored, model artifacts are approved for export, and corporate identity is mastered. It is not trusted by runtime by default. It produces signed release bundles.

**Controlled transfer zone** is the only bridge into the enclave. It performs static analysis, dependency scanning, malware scanning, SBOM validation, model provenance checks, license policy, signature verification, and human approval. Nothing crosses into the enclave without an immutable import record.

**Air-gapped enclave** contains the production control plane, data plane, identity services, model registry, observability stack, and GPU fleets. It has no NAT gateways, no public IPs, no public ingress, and no public package pulls. AWS service access is private-only through VPC endpoints and PrivateLink where AWS managed services are used.

## Section 4 - Tenant Tier Architecture In The Enclave

SIF-A preserves the three-tier consumption model from SIF, but each tier is enforced through enclave-local identity, policy, and capacity controls.

### Tier 1 - Pay-as-you-Go Shared Inference

- **Use cases:** experimentation inside the enclave, internal copilots for restricted teams, low-criticality summarization, model evaluation, controlled prototyping, and bursty workloads that cannot leave the boundary.
- **Isolation level:** logical isolation. Tenants share vLLM replicas and GPU capacity. Isolation is enforced by Sentinel Router identity, Kubernetes namespace boundaries, network policy, quota, model ACLs, and LMCache tenant namespaces.
- **SLA model:** best-effort inside the air-gapped cluster. Fair-share token quotas and bounded queues prevent a single tenant from exhausting shared capacity.
- **GPU and node strategy:** shared GPU node pool, aggressively packed by Karpenter. Models are deployed as shared runtime fleets where approved tenants route to the same base model.
- **KV cache strategy:** tenant-namespaced prefix and KV cache. Shared system prompts may be cached only when marked non-sensitive and approved by policy.
- **Cost model:** token-based chargeback. Input tokens, output tokens, model, tenant, and cost center are emitted as immutable cost events inside the enclave.
- **Security implication:** Tier 1 is the most cost-efficient tier, but it is not used for workloads requiring physical isolation or tenant-owned hardware.

### Tier 2 - Committed Capacity

- **Use cases:** production LOB workflows requiring guaranteed throughput in the enclave: restricted document reasoning, fraud operations, customer servicing assist, internal engineering copilots, and batch pipelines with predictable daily load.
- **Isolation level:** logical isolation with reservation. Tenants share cluster resources, but each committed tenant gets reserved throughput, routing priority, and KV headroom.
- **SLA model:** contractual. The platform commits to tokens/sec, TTFT/TPOT targets, and capacity floor. Over-quota bursts are admitted only when spare capacity exists.
- **GPU and node strategy:** provisioned NodePools with a capacity floor. Karpenter maintains enough nodes for the committed reservation and does not consolidate below the floor.
- **KV cache strategy:** LMCache partitions reserve a tenant-specific KV budget. KV-aware routing keeps sessions sticky to replicas with warm context.
- **Cost model:** committed capacity billing plus overage tokens. The LOB owns utilization risk for its reserved envelope.
- **Security implication:** Tier 2 is the default tier for regulated production workloads that need predictable service levels but not dedicated metal.

### Tier 3 - Dedicated Ultra-Low-Latency

- **Use cases:** deterministic latency paths, high-volume fraud decision support, sensitive modeling workflows, workloads requiring explicit tenant isolation, and teams that need host-level tuning.
- **Isolation level:** physical isolation. Dedicated GPU nodes, taints, tolerations, node labels, dedicated NVMe, dedicated LMCache, dedicated service identities, and tenant-specific network policy.
- **SLA model:** strict. Endpoint readiness gates include model warm-up, CUDA Graph capture, GPU topology validation, NUMA alignment, IRQ affinity, hugepage readiness, GDS validation, and policy admission.
- **GPU and node strategy:** dedicated Karpenter NodePool per tenant. No workload from another tenant can land on these nodes. Consolidation is disabled.
- **KV cache strategy:** dedicated HBM and NVMe-backed LMCache. No cross-tenant cache surface exists by construction.
- **Cost model:** full dedicated cost passthrough: GPU node-hours, NVMe, network, support overhead, and reserved standby.
- **Security implication:** Tier 3 is used when the LOB explicitly buys isolation, deterministic performance, and node-level control.

## Section 5 - Control Plane And Tenant Lifecycle

The air-gapped control plane is the product interface and the source of truth for platform intent. It is private to the enclave and backed by an internal database, GitOps repository, audit store, and policy engine.

### Tenant registration

When an LOB registers, the control plane creates:

- `tenant_id`, `lob_id`, `cost_center`, `data_classification`, `compliance_scope`, and `region`.
- Enclave-local identity mappings to Keycloak groups.
- Kubernetes namespaces for control, serving, observability, and optional build/runtime separation.
- Default `ResourceQuota`, `LimitRange`, `NetworkPolicy`, and Pod Security Admission labels.
- SPIFFE trust domain entries and workload identity templates.
- IAM role mappings for model registry access, logs, metrics, and cost event writes.
- Grafana folders, dashboards, and alert routes.
- Billing ledger keys and chargeback labels.

### Tenant endpoint request

The tenant requests:

- Tier 1, Tier 2, or Tier 3 capacity.
- Approved base model and model version.
- Approved LoRA adapters.
- Region or enclave placement.
- Compliance tags such as PCI, SOC2, internal restricted, or model-eval-only.
- Cost center and budget envelope.
- Network exposure profile: internal service, LOB-only endpoint, or restricted batch endpoint.

The control plane validates:

- Tenant quota and budget.
- Model access policy.
- LoRA adapter access policy.
- Data classification compatibility.
- Capacity availability.
- Security posture for the selected tier.
- Artifact availability in enclave-local registries.
- Required approvals for Tier 3 or restricted models.

### Declarative output

The control plane renders the tenant request into GitOps state:

```yaml
apiVersion: sentinel.capitalone.com/v1
kind: TenantEndpoint
metadata:
  name: fraud-assist-llama3-prod
  namespace: tenant-fraud-prod
  labels:
    sentinel.capitalone.com/tenant-id: fraud
    sentinel.capitalone.com/tier: "2"
    sentinel.capitalone.com/compliance: pci
spec:
  model:
    name: llama-3-70b-instruct
    version: "2026.06.01-approved"
    source: s3://sif-a-model-registry/approved/llama-3-70b/
  loraAdapters:
    - name: fraud-policy-style
      version: "12"
  capacity:
    committedTokensPerSecond: 8000
    maxContextTokens: 32768
    reservedKvGiB: 640
  routing:
    region: us-east-1-airgap
    kvAware: true
    prefillDecodeDisaggregation: true
  security:
    serviceAccount: fraud-assist-runtime
    spiffeId: spiffe://sif-a/tenant/fraud/workload/fraud-assist
    kmsKeyAlias: alias/sif-a/fraud/model-runtime
    networkProfile: tenant-restricted
  cost:
    costCenter: "LOB-FRAUD-ML"
    budgetPolicy: fraud-prod-budget
```

This CRD is not the runtime itself. It is the contract. Controllers render KServe `InferenceService`, RBAC, NetworkPolicy, SPIRE registration entries, IAM role bindings, model cache policy, dashboards, and cost metering rules from this one object.

## Section 6 - Authentication, Authorization, And RBAC

SIF-A uses separate identity paths for humans, workloads, Kubernetes APIs, cloud resources, and runtime requests. The paths converge at the control plane and Sentinel Router.

### Human authentication

Human access is handled by **Keycloak** running inside the enclave.

- Enterprise users and groups are imported into Keycloak through signed SCIM/LDIF snapshots from the controlled transfer zone.
- Keycloak is the OIDC issuer for the control plane UI, Grafana, Argo CD, Vault UI, and Kubernetes API authentication.
- MFA is enforced before enclave entry through privileged access workstation and bastion controls.
- Admin sessions are short-lived and logged.
- Break-glass users are local to the enclave, hardware-token protected, time-boxed, and require dual approval.

Human login path:

```
Engineer -> privileged workstation -> private bastion -> Keycloak OIDC
         -> control plane UI / kubectl / Grafana / Argo CD
```

### Workload identity

Workload identity is handled by **SPIRE/SPIFFE**.

- Every workload receives a SPIFFE ID based on namespace, service account, tenant, and workload role.
- mTLS between Sentinel Router, vLLM Router, vLLM workers, LMCache, metering collectors, and policy services is based on SPIFFE SVIDs.
- SPIRE agents run on every node and attest workloads from Kubernetes service account, namespace, node labels, and pod labels.
- The service mesh and Envoy gateways consume SPIFFE identities for peer authentication.

Example SPIFFE layout:

```text
spiffe://sif-a/platform/control-plane/api
spiffe://sif-a/platform/router/sentinel
spiffe://sif-a/tenant/fraud/workload/fraud-assist
spiffe://sif-a/tenant/cards/workload/card-servicing-assist
spiffe://sif-a/tenant/risk/lmcache/risk-llm-cache
```

### Kubernetes authentication

The Kubernetes API server trusts the enclave Keycloak OIDC issuer. Users never authenticate with long-lived kubeconfig certificates.

Kubernetes identity mapping:

```text
Keycloak group: sif-a-platform-admins      -> cluster-admin, gated by PAM approval
Keycloak group: sif-a-platform-sre         -> operational ClusterRoles, no secret read by default
Keycloak group: sif-a-security-auditors    -> read-only audit, policy, namespace, and logs
Keycloak group: tenant-fraud-admins        -> admin inside fraud namespaces only
Keycloak group: tenant-fraud-developers    -> endpoint request and read-only runtime access
Keycloak group: tenant-fraud-observers     -> dashboards and logs only
```

### Kubernetes RBAC model

RBAC is generated by the control plane. Tenants do not receive cluster-wide permissions.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: tenant-endpoint-operator
  namespace: tenant-fraud-prod
rules:
  - apiGroups: ["sentinel.capitalone.com"]
    resources: ["tenantendpoints"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
  - apiGroups: ["serving.kserve.io"]
    resources: ["inferenceservices"]
    verbs: ["get", "list", "watch"]
  - apiGroups: [""]
    resources: ["pods", "services", "events"]
    verbs: ["get", "list", "watch"]
```

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: tenant-fraud-admins
  namespace: tenant-fraud-prod
subjects:
  - kind: Group
    name: tenant-fraud-admins
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: tenant-endpoint-operator
```

### Application authorization

The Sentinel Router performs request-time authorization:

- Validate client mTLS identity.
- Validate OIDC/JWT claims where user delegation is used.
- Resolve `tenant_id`, `model_id`, `lora_id`, `cost_center`, and `data_classification`.
- Enforce model ACL and LoRA ACL.
- Enforce token quota and budget policy.
- Enforce region/enclave pinning.
- Enforce tier-specific routing.
- Emit audit record before forwarding to vLLM Router.

Authorization is fail-closed. If identity, policy, quota, or audit logging is unavailable, request admission stops before model execution.

### Cloud resource authorization

AWS resource access is scoped with IAM and private endpoints.

- IRSA maps Kubernetes service accounts to least-privilege IAM roles.
- S3 model paths are scoped per model family and tenant adapter.
- KMS keys are scoped by data class and tenant.
- STS, S3, ECR, EC2, KMS, CloudWatch, and Secrets Manager access is private-only through VPC endpoints where used.
- S3 bucket policies deny non-VPC endpoint access.
- ECR pull is allowed only from the enclave registry account.

## Section 7 - Security Architecture

SIF-A security is layered: boundary controls, identity, encryption, policy admission, runtime hardening, tenant isolation, audit, and evidence collection.

### Network boundary

- No public subnets in the runtime VPC.
- No NAT gateways.
- No public IP assignment on nodes, load balancers, or bastions.
- Private DNS zones only.
- Internal load balancers only.
- AWS APIs accessed through VPC endpoints and PrivateLink.
- Egress is default-deny at network policy, security group, and route-table layers.
- Controlled transfer is the only artifact ingress path.

```
Client App VPC -> PrivateLink / internal NLB -> Envoy Gateway
              -> Sentinel Router -> vLLM Router -> vLLM workers
```

### Encryption

- KMS or CloudHSM backed keys protect S3 model registry, EBS, FSx, logs, backups, and audit stores.
- Vault Transit protects application-level secrets and selected tenant payloads.
- SPIFFE mTLS protects service-to-service traffic.
- Node-local NVMe for model cache and KV spill is encrypted.
- Secrets are never stored in Git; GitOps references Vault paths.

### Secrets management

Vault runs inside the enclave.

- Vault PKI issues internal certificates where SPIFFE is not the correct identity primitive.
- Vault KV stores database credentials, signing key references, and one-time bootstrap tokens.
- Kubernetes workloads consume secrets through Vault Agent Injector or CSI driver.
- Dynamic credentials are preferred for databases and internal services.
- Root tokens are sealed, stored offline, and require break-glass procedure.

### Admission control

Gatekeeper or Kyverno enforces baseline security before pods are admitted.

Policy controls:

- Images must come from the enclave registry.
- Images must be signed by approved release keys.
- SBOM must exist and match the image digest.
- Pods must run as non-root except approved GPU/runtime images.
- Privileged pods are allowed only for approved DaemonSets such as GPU Operator, CNI, CSI, Falco, and node admission.
- HostPath mounts are denied except approved node-level agents.
- No public egress annotations are allowed.
- Tenant workloads must carry tenant, tier, model, cost center, and data-classification labels.
- Tier 3 workloads must schedule only on validated dedicated nodes.

Example image verification policy:

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: verify-enclave-images
spec:
  validationFailureAction: Enforce
  rules:
    - name: require-signed-enclave-image
      match:
        any:
          - resources:
              kinds: ["Pod"]
      verifyImages:
        - imageReferences:
            - "harbor.sif-a.local/*"
          attestors:
            - entries:
                - keys:
                    publicKeys: |-
                      -----BEGIN PUBLIC KEY-----
                      ENCLAVE_RELEASE_SIGNING_PUBLIC_KEY
                      -----END PUBLIC KEY-----
```

### Runtime security

- Falco/eBPF monitors unexpected shell, file write, network, and privilege activity.
- Kubernetes audit logs are shipped to the enclave audit store.
- Node audit logs include sudo, kernel module load, container runtime events, and GPU driver events.
- Runtime profiles are tuned for GPU workloads but still enforce least privilege.
- Sensitive debug endpoints are disabled or bound to localhost.
- Core dumps are disabled for model-serving pods unless an incident-specific approval exists.

### Tenant isolation

- Namespace per tenant and environment.
- Default-deny NetworkPolicy.
- Tenant-specific service accounts.
- Tenant-specific SPIFFE IDs.
- Tenant-specific KMS keys for restricted workloads.
- Tenant labels on every metric, trace, log, audit record, and cost event.
- LMCache tenant namespaces for prefix and KV cache.
- Dedicated physical nodes for Tier 3.

### Audit and compliance evidence

Every meaningful control-plane and data-plane action emits an audit event:

- Tenant registration.
- Policy change.
- RBAC change.
- Model approval.
- Artifact import.
- Endpoint provisioning.
- Runtime deployment.
- Request admission decision.
- Model invocation metadata.
- Cost event.
- Admin shell or break-glass session.
- Secret access.
- KMS decrypt event.

Audit events are immutable, write-once from the application perspective, and retained according to compliance class.

## Section 8 - Supply Chain And Artifact Import

The air gap is only credible if the platform can rebuild and operate without live access to public dependencies. SIF-A treats every artifact as governed supply chain material.

### Imported artifact classes

- Container images: KServe, vLLM, vLLM Router, LMCache, GPU Operator, DCGM, Envoy, OTel Collector, Prometheus, Grafana, Vault, Keycloak, Argo CD, policy controllers.
- Helm charts and Kustomize bundles.
- OS packages and node image packages.
- NVIDIA drivers, CUDA libraries, NCCL, GPUDirect Storage packages, and GPU firmware bundles.
- Python wheels, model-serving runtime dependencies, tokenizer packages.
- Model weights, tokenizer files, generation configs, quantized artifacts.
- LoRA adapters.
- Vulnerability databases for Trivy/Grype.
- OPA/Gatekeeper/Kyverno policy bundles.
- Documentation and runbooks.

### Import lifecycle

```
1. Build or retrieve artifact in connected enterprise zone.
2. Generate SBOM with Syft.
3. Run SAST/SCA/container scan with offline-compatible scanners.
4. Run license and export-control policy checks.
5. Generate provenance attestation.
6. Sign artifact and attestation with release key.
7. Package into immutable import bundle.
8. Scan bundle in controlled transfer zone.
9. Approve import with platform + security signoff.
10. Import into enclave registry/storage.
11. Verify signature again inside enclave.
12. Promote from quarantine to approved repository.
```

### Enclave artifact repositories

- **Harbor or private ECR:** container image registry with content trust and immutable tags.
- **OCI Helm repository:** charts and Kustomize bundles.
- **Nexus/Artifactory:** Maven, npm, PyPI wheelhouse, RPM/DEB mirrors where needed.
- **Private Git service:** GitLab/Gitea for enclave GitOps state and release manifests.
- **S3 model registry:** approved model weights, tokenizer artifacts, LoRA adapters, quantization metadata, and evaluation reports.
- **Vulnerability DB mirror:** signed snapshots of vulnerability databases imported on a fixed cadence.

### Promotion gates

An artifact cannot be used by production until it has:

- Immutable digest.
- SBOM.
- Signature.
- Provenance attestation.
- Scan result.
- License approval.
- Owner.
- Expiration or review date.
- Promotion record.

The control plane will not render an endpoint if the requested image, model, adapter, policy bundle, or runtime dependency is not present in the approved enclave repositories.

## Section 10 - End-To-End Flow

### 1. Artifact import

The platform release bundle is built in the connected enterprise zone and imported through the controlled transfer zone. Images, charts, model artifacts, policy bundles, and vulnerability DB snapshots are scanned, signed, and promoted to enclave-local repositories.

### 2. Identity snapshot import

Enterprise user and group membership is exported as a signed snapshot. The transfer zone validates the snapshot, and Keycloak imports it into the enclave. Group changes become effective only after import and audit.

### 3. LOB registration

The LOB registers through the control plane UI. The control plane creates tenant records, namespace templates, RBAC bindings, SPIFFE registration entries, IAM mappings, cost labels, dashboards, and default policies.

### 4. Capacity request

The LOB requests Tier 1, Tier 2, or Tier 3 capacity, selects an approved model, attaches approved LoRA adapters, sets compliance tags, and assigns cost center.

### 5. Policy and capacity validation

The control plane validates model eligibility, LoRA eligibility, tenant quota, data classification, cost policy, and capacity. It also verifies all required artifacts exist in approved enclave repositories.

### 6. GitOps render

The control plane renders:

- `TenantEndpoint` CR.
- KServe `InferenceService`.
- Service accounts.
- RoleBindings.
- NetworkPolicies.
- SPIRE registration entries.
- IAM role bindings.
- Vault secret paths.
- LocalModelCache policy.
- Prometheus scrape config.
- Grafana folder and dashboard definitions.
- Cost metering rules.

### 7. Admission control

Argo CD applies the rendered resources. Gatekeeper/Kyverno verifies:

- Image registry is enclave-local.
- Image digest is signed.
- Tenant labels are present.
- Namespace is authorized.
- Pod security policy is satisfied.
- Tier placement rules are satisfied.
- No prohibited egress exists.

### 8. Node and pod bootstrap

Karpenter provisions or reuses GPU nodes. NVIDIA GPU Operator validates driver and device plugin state. KServe starts vLLM Router, vLLM workers, and LMCache services. SPIRE issues SVIDs to workloads.

### 9. Model staging

The model moves from private S3 to FSx for Lustre, then to node-local NVMe through LocalModelCache. Tier 3 uses GDS validation before readiness. LoRA adapters are staged separately and mounted with tenant-specific access controls.

### 10. Runtime warm-up

The endpoint is not ready until:

- Model files are present locally.
- vLLM workers have loaded weights.
- Tokenizer is loaded.
- CUDA Graphs are captured where used.
- LMCache is initialized.
- First warm inference succeeds.
- Telemetry exporters are live.
- Tier 3 node validation is green where applicable.

### 11. Request path

```
Client -> private endpoint -> Envoy Gateway -> Sentinel Router
       -> vLLM Router -> prefill worker -> LMCache -> decode worker
       -> token stream -> Sentinel Router -> client
```

### 12. Request authorization

Sentinel Router validates identity, tenant, model ACL, LoRA ACL, quota, budget, data classification, and region. The request fails closed if any control is unavailable.

### 13. KV-aware routing

vLLM Router uses LMCache metadata to route requests to replicas with warm KV or prefix state. Tenant namespace is part of the cache key, so cross-tenant cache hits are impossible.

### 14. Telemetry and cost

OpenTelemetry spans, Prometheus metrics, logs, audit records, token counts, GPU allocation, and cost events are emitted inside the enclave. Dashboards and chargeback reports are generated without external telemetry services.

## Section 11 - Storage Architecture

SIF-A storage is designed for deterministic model availability and strict data custody.

```
Approved import bundle
        |
        v
Private S3 model registry  (authoritative, KMS encrypted, versioned)
        |
        v
FSx for Lustre             (warm shared high-throughput model cache)
        |
        v
LocalModelCache            (KServe readiness barrier)
        |
        v
Node-local encrypted NVMe  (model cache + KV spill)
        |
        v
GPU HBM                    (weights + active KV cache)
```

### Model registry

The private S3 model registry stores:

- Base weights.
- Quantized weights.
- Tokenizer artifacts.
- Model config.
- Generation config.
- LoRA adapters.
- Evaluation reports.
- Approval metadata.
- SBOM and provenance.
- Data-classification tags.

Bucket policy denies any request outside the enclave VPC endpoint. KMS keys are separated by model classification and tenant sensitivity.

### FSx for Lustre

FSx for Lustre acts as the warm fan-out layer. Large model files are read once from S3 into Lustre and then fanned out to multiple GPU nodes at high throughput. This prevents S3 from becoming the cold-start bottleneck during scale-out.

### LocalModelCache

LocalModelCache is the readiness boundary. A pod is not considered ready until the model is present on node-local storage and checksum validation passes. Runtime never downloads from public sources and never reads model weights from S3 in the hot path.

### NVMe and KV spill

Node-local NVMe stores:

- Model files staged for the node.
- Tokenizer cache.
- LMCache spill files.
- Tier-specific runtime scratch space.

Tier 3 NVMe is dedicated to the tenant and aligned to the GPU/NUMA domain. Tier 1 and Tier 2 use per-tenant directories and encryption boundaries.

### GPUDirect Storage

Tier 3 validates GPUDirect Storage for direct NVMe-to-GPU DMA. The GDS path is required before production traffic can be admitted.

Validation commands:

```bash
gdscheck -p
/usr/local/cuda/gds/tools/gdsio -f /mnt/nvme0/model.safetensors -d 0 -w 8 -s 1G -x 0
nvidia-smi topo -m
```

## Section 12 - Host, GPU, And Node Security

The node is part of the security boundary. SIF-A treats node configuration as signed, validated, and continuously monitored.

### Node image

- Built from an approved base image.
- Includes pinned kernel, container runtime, GPU driver, CUDA, NCCL, GDS, CNI, CSI, and hardening packages.
- Signed and promoted through the same artifact import process.
- No runtime package installation from public repositories.
- Immutable after boot except approved DaemonSet-managed state.

### GPU node validation

Every GPU node must pass:

```bash
nvidia-smi
nvidia-smi topo -m
nvidia-smi nvlink --status
dcgmi discovery -l
lsmod | grep nvidia
lsmod | grep nvidia_peermem
```

### Tier 3 host tuning

Tier 3 dedicated nodes apply:

```bash
isolcpus=8-47,56-95 nohz_full=8-47,56-95 rcu_nocbs=8-47,56-95
intel_iommu=on iommu=pt transparent_hugepage=never
hugepagesz=2M hugepages=8192 default_hugepagesz=2M
```

Tier 3 kubelet policy:

```yaml
cpuManagerPolicy: static
memoryManagerPolicy: Static
topologyManagerPolicy: single-numa-node
topologyManagerScope: container
reservedSystemCPUs: "0-7"
```

IRQ affinity:

```bash
systemctl disable --now irqbalance
for irq in $(grep -E 'mlx5|nvme' /proc/interrupts | awk '{print $1}' | tr -d :); do
  echo 0-7 > /proc/irq/$irq/smp_affinity_list
done
```

Node admission DaemonSet checks:

- Isolated CPUs are active.
- Hugepages are reserved per NUMA node.
- NIC, NVMe, and GPU topology is aligned.
- NVLink is healthy.
- GDS is supported.
- RDMA peer memory module is loaded where required.
- DCGM is reporting.
- Kernel command line matches approved profile.
- No prohibited kernel modules are loaded.

Only validated nodes receive:

```text
sentinel.capitalone.com/tier3-validated=true
```

Tier 3 pods require this label and tolerate only the tenant-specific taint.

## Section 15 - Operational Excellence

SIF-A is operated as a product, not as a collection of isolated clusters.

### GitOps lifecycle

- All platform and tenant state is declared in private Git.
- Argo CD reconciles approved state only.
- Direct `kubectl apply` to production namespaces is blocked except break-glass.
- Pull requests require platform owner approval and security approval for policy-sensitive changes.
- Every deployment is traceable to commit, artifact digest, SBOM, and approval record.

### Release lifecycle

```
source commit -> build -> scan -> sign -> transfer -> enclave promote
             -> canary -> evaluate -> promote -> audit record
```

### Canary and blue/green

- New model/runtime versions deploy as KServe revisions.
- Canary receives a controlled traffic slice.
- Promotion gates on TTFT, TPOT, error rate, GPU health, policy denies, and quality eval.
- Blue revision remains drainable for rollback.

### Readiness and warm-up

Endpoint readiness requires:

- Model staged locally.
- Checksum verified.
- vLLM loaded.
- LMCache initialized.
- Warm inference complete.
- Telemetry active.
- Auth and policy checks healthy.
- Tier 3 node admission green.

### Backup and disaster recovery

Backups remain inside the enclave or move through approved encrypted export.

Backed up objects:

- Control plane database.
- Private Git repositories.
- Harbor/ECR metadata.
- Model registry metadata.
- Vault encrypted snapshots.
- Keycloak configuration.
- Grafana dashboards.
- Prometheus/Mimir long-term metrics.
- Audit store.
- Cost ledger.

Recovery is tested through enclave-local restore drills. A restored cluster must prove model serving, identity, policy, audit, observability, and cost metering before it is accepted.

### Incident response

SIF-A incidents are handled with evidence-first operations:

- Freeze relevant GitOps state.
- Preserve audit logs and traces.
- Snapshot affected namespaces.
- Quarantine suspect images or models.
- Disable endpoint route at Sentinel Router.
- Revoke SPIFFE registration or Vault secret path if identity is compromised.
- Rotate keys where required.
- Produce incident evidence bundle from enclave stores.

### Cluster-wide circuit breakers

Sentinel Router and vLLM Router enforce:

- Per-tenant queue limits.
- Per-model concurrency limits.
- KV pressure shedding.
- GPU saturation protection.
- Tier priority.
- Fail-closed behavior on auth, policy, or audit unavailability.

## Section 17 - Future Improvements

- **Confidential accelerator attestation:** integrate GPU and node attestation into admission so sensitive Tier 3 workloads prove the hardware and driver stack before serving.
- **Deterministic enclave rebuilds:** make the entire platform reconstructable from signed import bundles, private Git, and encrypted backups with no public dependency.
- **CXL-backed KV tier:** add CXL memory as a middle KV tier between HBM and NVMe for larger working sets in the enclave.
- **3-tier KV cache:** standardize HBM -> CXL -> NVMe caching policy with tenant-aware eviction and cost attribution.
- **Policy-as-code evidence automation:** generate PCI/SOC2 control evidence automatically from GitOps commits, admission decisions, audit logs, and runtime telemetry.
- **Model risk workflow integration:** tie model approval, eval reports, drift checks, and LoRA approvals directly to endpoint provisioning gates.
- **Cross-enclave federation:** support controlled model and policy promotion between enclaves using signed bundles and explicit governance, without introducing runtime network coupling.
